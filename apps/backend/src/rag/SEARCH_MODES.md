# RAG search modes

Краткая выжимка по режимам поиска в RAG-модуле: как они работают, когда их лучше применять и какие у них ограничения.

## Dense search

**Механика:** вопрос превращается в embedding, затем Qdrant ищет chunks с близкими embedding-векторами.

**Когда применять:**
- смысловые вопросы без точных ключевых слов;
- переформулированные вопросы;
- вопросы, где важна близость смысла, а не совпадение терминов.

**Плюсы:**
- хорошо ловит семантику;
- может найти релевантный текст, даже если слова в вопросе и документе отличаются;
- удобен для естественных пользовательских вопросов.

**Минусы:**
- может промахнуться по точному факту, если нужный chunk семантически похож на соседние;
- хуже работает с редкими именами, датами, названиями и точными формулировками;
- score нельзя напрямую сравнивать со score других режимов.

## BM25 search

**Механика:** локальный лексический поиск по токенам. Чем лучше совпадают слова вопроса со словами chunk, тем выше chunk в выдаче.

**Когда применять:**
- в вопросе есть точные имена, термины, даты или уникальные фразы;
- нужно найти конкретное место в документе;
- пользователь почти цитирует документ.

**Плюсы:**
- хорошо находит редкие ключевые слова;
- прозрачно объясняется;
- не требует embedding-запроса для поиска по уже загруженным chunks.

**Минусы:**
- слабее на переформулированных смысловых вопросах;
- не понимает синонимы и близкий смысл так же хорошо, как dense;
- может поднять chunk только из-за совпадения слов, даже если он хуже отвечает на вопрос.

## Sparse search

**Механика:** вопрос и chunks превращаются в sparse vectors: разреженные векторы токенов. Эти sparse vectors хранятся и ищутся в Qdrant.

**Когда применять:**
- нужен keyword-like поиск, но внутри Qdrant, а не в памяти backend;
- важно хранить dense и lexical-сигналы рядом с одним payload;
- нужно приблизиться к production hybrid-поиску через vector database.

**Плюсы:**
- работает через Qdrant, как dense search;
- хорошо ловит точные токены, имена и термины;
- может использоваться в hybrid вместе с dense без отдельной локальной BM25-таблицы.

**Минусы:**
- текущая реализация использует локальный hashing/token-frequency sparse vector, это не полноценная learned sparse model;
- score не равен BM25 score;
- требует переиндексации коллекции с named vectors `dense` и `sparse`.

## Hybrid search

**Механика:** запускаются dense search и Qdrant sparse search, затем результаты объединяются через RRF (Reciprocal Rank Fusion). RRF учитывает позиции chunks в обоих списках, а не пытается смешивать разные score напрямую.

**Когда применять:**
- нужен быстрый основной режим без rerank;
- вопрос может содержать и смысловую часть, и точные слова;
- нужно повысить стабильность относительно одного dense или одного BM25.

**Плюсы:**
- совмещает смысловой и Qdrant lexical/sparse поиск;
- обычно стабильнее одиночных режимов;
- хорошо подходит как быстрый fallback для UI.

**Минусы:**
- RRF score обычно маленький, например `0.03`, и это нормально;
- top-1 не всегда будет самым точным chunk;
- объединение рангов не заменяет полноценный rerank.

## Advanced search

**Механика:** сначала выполняется hybrid search, затем top candidates переоцениваются reranker-ом. В текущей NestJS-реализации rerank делает LLM scoring с fallback на эвристический rerank.

**Когда применять:**
- основной пользовательский режим по умолчанию;
- важен лучший top-1 chunk;
- вопрос требует выбрать самый ответный фрагмент среди нескольких похожих chunks;
- нужно показать наиболее качественный RAG-сценарий.

**Плюсы:**
- чаще поднимает самый релевантный chunk наверх;
- исправляет случаи, когда hybrid нашел нужный chunk, но не поставил его первым;
- лучше подходит для финального ответа пользователю.

**Минусы:**
- медленнее и дороже, чем hybrid;
- rerank score имеет свою шкалу `0..1` и не сравнивается напрямую с dense/BM25/RRF;
- финальный ответ может быть более кратким, даже если найден правильный chunk.

## HyDE + Hybrid search

**Механика:** LLM сначала пишет короткий гипотетический фрагмент документации, который мог бы отвечать на вопрос. Затем этот фрагмент используется как поисковый запрос для hybrid search.

**Когда применять:**
- пользовательский вопрос сформулирован бытовым языком;
- в вопросе мало терминов из документации;
- нужно преодолеть словарный разрыв между вопросом и документом.

**Плюсы:**
- может улучшить поиск, если LLM удачно добавила доменные термины;
- работает поверх уже существующего hybrid, поэтому сохраняет lexical + dense сигналы;
- хорошо демонстрирует продвинутые RAG-приемы из задания.

**Минусы:**
- медленнее и дороже обычного hybrid;
- качество зависит от гипотетического документа;
- если LLM добавит неверные детали, поиск может уйти в сторону.

## MultiQuery + Hybrid search

**Механика:** LLM генерирует несколько альтернативных формулировок исходного вопроса. Для исходного вопроса и каждой reformulation запускается hybrid search, затем результаты объединяются через RRF.

**Когда применять:**
- пользовательский вопрос неоднозначный;
- один запрос может не покрывать все полезные формулировки;
- нужно повысить recall за счет нескольких вариантов запроса.

**Плюсы:**
- повышает шанс найти релевантный документ разными формулировками;
- хорошо работает для перефразированных вопросов;
- остается объяснимым: можно смотреть, какие reformulations были использованы.

**Минусы:**
- делает несколько поисковых проходов;
- требует LLM-запроса;
- может добавить шум, если reformulations слишком далеко ушли от исходного вопроса.

## Recommended usage

| Сценарий | Лучший режим |
| --- | --- |
| Основной режим для пользователя | Advanced |
| Быстрый режим без rerank | Hybrid |
| Смысловой вопрос без точных слов | Dense или Advanced |
| Вопрос с редкими словами, именами, датами | Sparse, BM25 или Advanced |
| Проверка Qdrant lexical-поиска | Sparse |
| Сильный словарный разрыв | HyDE + Hybrid |
| Неоднозначный или широкий запрос | MultiQuery + Hybrid |
| Debug и сравнение алгоритмов | BM25, Sparse, Dense, Hybrid, HyDE, MultiQuery, Advanced |

## Score interpretation

Scores разных режимов не являются одной общей шкалой.

| Режим | Что означает score |
| --- | --- |
| Dense | vector similarity из Qdrant |
| BM25 | нормализованный лексический score |
| Sparse | sparse vector score из Qdrant |
| Hybrid | RRF score, маленькие значения нормальны |
| HyDE + Hybrid | RRF score после поиска по гипотетическому документу |
| MultiQuery + Hybrid | RRF score после объединения нескольких hybrid-выдач |
| Advanced | rerank relevance score `0..1` |

Для UI лучше показывать пользователю позицию chunk (`#1`, `#2`, `#3`), а score оставлять в debug/details с подписью конкретной метрики.

## Architecture and flow

Все режимы проходят через общий вход:

1. `POST /api/rag/search`, `POST /api/rag/ask` или `POST /api/rag/ask/stream`.
2. `RagController` передает request в `RagService`.
3. `retrieve()` нормализует вопрос, режим поиска, лимит и threshold.
4. `searchByMode()` выбирает конкретный алгоритм: `denseSearch`, `bm25Search`, `qdrantSparseSearch`, `hybridSearch`, `hydeSearch`, `multiQuerySearch` или `advancedSearch`.
5. Найденные chunks возвращаются в UI или передаются в `generateAnswer()` для генерации финального ответа.

Перед поиском документы должны быть проиндексированы через `POST /api/rag/index`. Индексация делает три вещи:

- режет файлы из `RAG_DOCS_DIR` на chunks;
- сохраняет named vectors `dense` и `sparse` в Qdrant;
- держит indexed chunks в cache сервиса, чтобы локальный BM25 работал с теми же chunks.

### Dense architecture

Pipeline:

1. `denseSearch(query, k, threshold)` получает вопрос.
2. `embed([query])` отправляет вопрос в embedding model.
3. Qdrant получает named vector query `using: "dense"` через `/points/query`.
4. Qdrant возвращает top-k chunks по vector similarity.
5. Сервис отбрасывает результаты ниже threshold и возвращает `RagChunk[]`.

Логика ranking:

- основной сигнал: близость embedding-векторов;
- чем ближе вопрос и chunk в embedding space, тем выше chunk;
- `score` и `denseScore` отражают similarity из Qdrant.

Практический смысл:

- dense не ищет точные слова;
- он ищет похожий смысл;
- поэтому он хорош для переформулировок, но может пропустить точный факт.

### BM25 architecture

Pipeline:

1. `bm25Search(query, k)` получает вопрос.
2. Сервис берет indexed chunks из cache.
3. Вопрос и chunks токенизируются через общий tokenizer.
4. Для каждого chunk считается BM25 score.
5. Результаты сортируются по score и обрезаются до top-k.

Логика ranking:

- основной сигнал: совпадение токенов вопроса и chunk;
- редкие слова дают больший вклад, чем частые;
- длина chunk учитывается, чтобы длинные chunks не получали нечестное преимущество;
- score нормализуется относительно лучшего результата, поэтому top result обычно получает `1`.

Практический смысл:

- BM25 отлично находит `Аннушка`, `подсолнечное масло`, `Понтий Пилат`, `МАССОЛИТ`;
- BM25 хуже, если пользователь задает вопрос другими словами и не использует термины из документа.

### Sparse architecture

Pipeline:

1. `qdrantSparseSearch(query, k)` получает вопрос.
2. `createSparseVector(query)` токенизирует текст, хэширует токены в integer indices и считает normalized term-frequency values.
3. Qdrant получает sparse query `using: "sparse"` через `/points/query`.
4. Qdrant возвращает top-k chunks по sparse vector score.
5. Сервис возвращает `score`, `sparseScore` и retrieval tag `sparse`.

Логика ranking:

- основной сигнал: совпадение токенов sparse query и sparse vector chunk;
- score приходит из Qdrant;
- это keyword-like поиск, но физически выполняется в vector database.

Практический смысл:

- Sparse похож по назначению на BM25, но живет в Qdrant;
- удобно для production hybrid, где dense и sparse vectors хранятся в одной коллекции;
- текущая реализация не требует отдельной embedding/LLM-модели для sparse vector.

### Hybrid architecture

Pipeline:

1. `hybridSearch(query, finalK, candidateLimit)` запускает два поиска параллельно:
   - `denseSearch(query, candidateLimit)`;
   - `qdrantSparseSearch(query, candidateLimit)`.
2. Каждый поиск возвращает свой ranked list.
3. `reciprocalRankFusion()` объединяет списки по позициям.
4. Сервис собирает merged chunks, добавляет `denseScore`, `sparseScore`, `rrfScore` и `retrieval`.
5. Результат сортируется по `rrfScore` и обрезается до `finalK`.

Логика ranking:

RRF не сравнивает dense score и BM25 score напрямую. Вместо этого он смотрит на место chunk в каждом списке:

```text
RRF score = sum(1 / (k + rank))
```

В коде используется `k = 60`, поэтому хорошие RRF scores выглядят маленькими: `0.03` может быть нормальным высоким значением.

Практический смысл:

- если chunk высоко и в dense, и в sparse, он почти наверняка поднимется;
- если chunk найден только одним способом, он тоже может попасть в выдачу;
- hybrid повышает recall, но не всегда дает лучший top-1.

### Advanced architecture

Pipeline:

1. `advancedSearch(query, k)` сначала вызывает `hybridSearch(query, HYBRID_CANDIDATE_LIMIT, HYBRID_CANDIDATE_LIMIT)`.
2. Hybrid возвращает набор кандидатов.
3. `rerank(query, candidates, k)` просит reranker оценить прямую полезность каждого candidate для ответа на вопрос.
4. Candidates получают `rerankScore`.
5. Результаты сортируются по `rerankScore` и обрезаются до top-k.

Логика ranking:

- hybrid отвечает за широкий сбор кандидатов;
- rerank отвечает за точный порядок;
- если LLM rerank недоступен или возвращает некорректный JSON, включается `heuristicRerank()`;
- heuristic rerank считает покрытие токенов вопроса в тексте chunk и добавляет небольшой bonus от `rrfScore`.

Практический смысл:

- advanced обычно лучший режим для конечного пользователя;
- он особенно полезен, когда нужный chunk уже есть среди hybrid candidates, но не находится на первом месте;
- цена этого качества: дополнительный LLM-запрос, latency и стоимость.

### HyDE architecture

Pipeline:

1. `hydeSearch(query, k)` получает исходный вопрос.
2. `generateHypotheticalDocument(query)` просит chat model написать короткий технический фрагмент документации.
3. Полученный hypothetical document передается в `hybridSearch(hypotheticalDocument, k)`.
4. Результаты помечаются тегом `hyde`.

Логика ranking:

- ranking остается hybrid/RRF;
- LLM не ранжирует документы напрямую;
- LLM только превращает вопрос в более документоподобный поисковый текст.

Практический смысл:

- полезно, когда вопрос пользователя и документ используют разный словарь;
- риск в том, что hypothetical document может добавить нерелевантные термины.

### MultiQuery architecture

Pipeline:

1. `multiQuerySearch(query, k)` получает исходный вопрос.
2. `generateQueryReformulations(query)` просит chat model создать 3 альтернативные формулировки.
3. Для исходного вопроса и каждой reformulation запускается `hybridSearch()`.
4. Все ranked lists объединяются через `reciprocalRankFusion()`.
5. Результаты помечаются тегом `multiQuery`.

Логика ranking:

- каждый вариант вопроса дает свой hybrid ranked list;
- RRF поднимает документы, которые стабильно находятся разными формулировками;
- score остается RRF score, а не LLM confidence.

Практический смысл:

- повышает recall;
- может помочь, если одна формулировка не попала в нужный документ;
- может добавить шум, если reformulations слишком широкие.

### Evaluation architecture

Endpoint `POST /api/rag/evaluate` повторяет идею `s21/activities/dev/week-2/1-day/run.py`:

1. Берет `small` или `full` S21 dataset.
2. Для каждого вопроса запускает `BM25`, `Sparse`, `Dense`, `Hybrid (RRF)`, `HyDE + Hybrid`, `MultiQuery + Hybrid`.
3. Сравнивает top-k `docId` с `relevantIds`.
4. Считает `hit_rate`, `MRR` и `precision@k`.
5. Сохраняет markdown-отчет в `RAG_RESULTS_PATH`.

### Answer generation

Поиск и генерация ответа - разные этапы:

1. Search modes выбирают chunks.
2. `generateAnswer()` получает вопрос и найденные chunks.
3. Chat model формирует ответ только на основе найденного контекста.

Из-за этого более высокий search quality не всегда означает более длинный ответ. Например, advanced может найти правильный chunk, но финальная модель даст краткий ответ. Оценивать поиск лучше по top chunks, а финальный ответ - отдельно.

## Practical conclusion

Для обычного пользователя лучше ставить **Advanced** как режим по умолчанию: он объединяет dense и Qdrant sparse, а затем переоценивает кандидатов. Для сравнения именно по заданию используйте методы из `run.py`: **BM25**, **Dense**, **Hybrid (RRF)**, **HyDE + Hybrid**, **MultiQuery + Hybrid**. Для проверки Qdrant sparse отдельно используйте **Sparse**. Если важны скорость и стоимость, лучший компромисс - **Hybrid**.
