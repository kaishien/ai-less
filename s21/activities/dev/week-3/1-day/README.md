# День 9 (Неделя 3) • Практика: мультиагентные системы

Одиночный агент упирается в три ограничения: контекстное окно заканчивается на больших задачах, специализация размывается когда один агент делает всё, параллелизм невозможен без разделения работы. Мультиагентная архитектура — способ распределить задачу между независимыми единицами, каждая из которых отвечает за свою область. Выберите минимум три задачи из пяти.

---

## Задача 1: Служба поддержки (Supervisor)

Supervisor анализирует входящий запрос и маршрутизирует его к одному из трёх специализированных агентов.

**Задание:**
1. Определите `SupervisorState` с полями `messages`, `next_agent`, `final_answer`
2. `supervisor_node`: LLM с `with_structured_output(RouteDecision)`, где `next: Literal["tech_support", "billing", "sales", "FINISH"]`
3. После ответа любого субагента — граф возвращается к Supervisor, который завершает (`FINISH`)
4. Проверьте на трёх разных обращениях — маршрутизация должна работать корректно

**Промпт:**
```
Напиши LangGraph Supervisor граф для службы поддержки.
SupervisorState с add_messages. Supervisor делает with_structured_output для RouteDecision.
Три субагента (TechSupport, Billing, Sales) с system-промптами своей специализации.
После субагента — ребро обратно к supervisor.
Conditional edge из supervisor: RouteDecision.next → нужный агент или END.
```

**На что обратить внимание:** Supervisor — единая точка маршрутизации, что удобно для аудита и отладки, но создаёт узкое место: при высокой нагрузке или сложной логике маршрутизации вся система зависит от одного узла.

## Задача 2: Автоматическое код-ревью (Swarm)

Developer пишет код, QA проверяет — цикл продолжается до тех пор, пока QA не выдаст LGTM или не исчерпается лимит ревизий.

**Задание:**
1. `Developer` — получает задачу или замечания QA, пишет или правит код
2. `QA` — проверяет код: если проблем нет — пишет `LGTM`, иначе — список замечаний
3. Conditional edge после QA: если `"LGTM"` в ответе → `END`, иначе → `Developer`
4. Добавьте счётчик итераций в state (`revision_count`) — завершайте граф если `revision_count >= 3`
5. Проверьте: попросите написать функцию с намеренной ошибкой — сколько итераций потребовалось?

**Промпт:**
```
Напиши LangGraph Swarm: Developer и QA в цикле.
State: messages (add_messages) + revision_count (int, суммируется через operator.add).
QA пишет LGTM если код хороший, иначе — замечания.
Conditional edge: если LGTM в последнем сообщении QA → END, иначе → Developer.
Добавь защиту: если revision_count >= 3 → END принудительно.
```

**На что обратить внимание:** Swarm позволяет агентам самим решать кому передать управление, но без явного ограничения ревизий граф легко уходит в бесконечный цикл — счётчик и защита обязательны в production.

## Задача 3: Пайплайн перевода (Supervisor с последовательностью)

Supervisor управляет двумя агентами в строгом порядке: Translator → Editor → FINISH.

**Задание:**
1. Supervisor **всегда** сначала направляет к `Translator`, затем к `Editor`, затем `FINISH`
2. Translator: черновой перевод на русский
3. Editor: вычитка — исправляет стиль, грамматику, звучание
4. State хранит черновик и финальный перевод в отдельных полях

**Подсказка:** Supervisor отслеживает текущий шаг через поле `stage: Literal["translate", "edit", "done"]`.

**Промпт:**
```
LangGraph Supervisor для пайплайна перевода.
State: input_text, draft_translation, final_translation, stage.
Supervisor: if stage == "translate" → Translator, if stage == "edit" → Editor, else FINISH.
Каждый агент обновляет нужное поле + stage.
Не используй add_messages — используй обычные поля TypedDict.
```

**На что обратить внимание:** последовательный Supervisor — самый предсказуемый паттерн: порядок выполнения жёстко задан, легко тестировать каждый этап изолированно. Цена — отсутствие гибкости при изменении пайплайна.

## Задача 4: Клуб дебатов с раундами (Swarm + reducer)

Два агента дискутируют на заданную тему, Moderator подводит итог после минимум трёх раундов.

**Задание:**
1. `Proponent` — аргументы «За»
2. `Opponent` — аргументы «Против», после каждого ответа увеличивает `round`
3. Кастомный reducer для `round`: `lambda a, b: a + b` (аккумулятор)
4. Conditional edge: если `round >= 3` → `moderator` → `END`
5. Moderator подводит итог дебатов

**Промпт:**
```
LangGraph дебаты: Proponent и Opponent, счётчик раундов.
State: messages (add_messages) + round: Annotated[int, operator.add].
Opponent возвращает {"round": 1} чтобы инкрементировать.
Conditional edge после Opponent: if state["round"] >= 3 → moderator → END.
Moderator: анализирует все аргументы и пишет сбалансированный вывод.
```

**На что обратить внимание:** кастомный reducer позволяет аккумулировать числовые метрики без явного чтения предыдущего значения — паттерн применим для любых счётчиков и агрегатов в мультиагентном state.

## Задача 5: Research + Writer (Handoff через Command)

Planner составляет план, Writer реализует, Critic оценивает — без центрального контроллера.

**Задание:**
1. `Planner` возвращает `Command(update={"plan": ...}, goto="writer")`
2. `Writer` получает план и пишет статью, возвращает `Command(update={"article": ...}, goto="critic")`
3. `Critic` оценивает статью: если нужна правка → `Command(update={"critique": ...}, goto="writer")`, иначе → `Command(goto=END)`
4. Максимум 2 ревизии — защита через `revision_count` в state

**Промпт:**
```
LangGraph Handoff через Command: Planner → Writer → Critic.
Planner: Command(update={"plan": plan}, goto="writer").
Writer: генерирует article, Command(goto="critic").
Critic: оценивает, если нужна правка → Command(update={"critique": ...}, goto="writer"),
иначе Command(goto=END). Добавь поле revision_count в state с защитой >= 2.
```

**На что обратить внимание:** Handoff через Command даёт максимальную гибкость — каждый агент сам определяет следующий шаг. Нет центрального контроллера, но это усложняет отладку: поток управления разбросан по узлам, важно трейсить каждый Command.

---

## Выбор паттерна

- **Supervisor** — когда нужна предсказуемая маршрутизация и единая точка контроля
- **Swarm** — когда агенты должны сами решать кому передать управление, допустимы итерации
- **Handoff через Command** — когда нужна максимальная гибкость без центрального контроллера
